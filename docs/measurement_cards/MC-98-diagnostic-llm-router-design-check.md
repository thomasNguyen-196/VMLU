# MC-98 — Muse Spark 1.3 (OpenCode Go), LLM router design check: one group per ViBidLQA design item

Registered 2026-10-28 (+07) before benchmark-item requests of this card. The design is `openspec/changes/diagnostic-llm-router`. It does not change MC-90 to MC-97: their registered text, manifests, rules, procedures and analyses stand.

| Field | Condition |
| --- | --- |
| Why | MC-97 measured the menu on the 967 wide reading items; all scores below are token-F1.<br>• Q (62.7 on ViBidLQA) is below B (64.6) and S (65.9).<br>• Choosing an arm per item on one draw and scoring the other reaches 73.3 pooled, against 73.06 for the per-dataset rule. On ViBidLQA it reaches 67.4, against 65.9 for always-S.<br>• A post hoc keyword grouping of the question text found one group with a clear, repeated difference: "which article or clause" questions, where B scores 64.8 against 58.9 for S.<br>After seeing this, the project owner chose a quick check of the LLM router on the design items before any held-out evaluation. It asks whether Muse Spark 1.3, reading the passage and the question, sorts the ViBidLQA questions into groups that separate where B, Q or S wins better than the keyword grouping and better than always-S. |
| Scope | The 591 ViBidLQA test items of the menu set (`data/diagnostic_llm_router/menu_q_v1.json`), in manifest order, one router call each. No student-model request is sent; the student's draws are those of MC-90 to MC-92 (B, S) and MC-97 (Q). Manifest `data/diagnostic_llm_router/router_labels_v1.json`, self-hash `53692d0864af5c9bbb9f7d95c1dcbd7bead6de355eab49eb2efce32f7ec99743`, run identity `dataset:item:router-1`. |
| Router prompt | `data/diagnostic_llm_router/router_v1.json`, SHA-256 `15ffc94b06a10df0b2fe924a7760ecae2a5d6f867d1f5f387f711987ca127df8` (`muse-router-v1`).<br>The prompt is in Vietnamese and has four parts:<br>• It asks the model to sort the question into exactly one group and not to answer it.<br>• It lists the six groups in order. When a question fits several, the earlier group wins.<br>• It gives the passage and the question of the item's frozen reading prompt.<br>• It asks for a last line `Nhóm: <id>`.<br>The groups, written from the MC-97 design draws:<br>• `so_hieu`: asks for the number or name of an article, clause, point, chapter or document;<br>• `tinh_toan`: the answer needs a calculation, a count, a comparison or several facts combined;<br>• `toan_bo`: asks for a whole list or the whole content of a provision;<br>• `mot_phan`: the passage lists several items or a long provision and the question asks for one of them;<br>• `dieu_kien`: asks for a condition, case, time of application or consequence;<br>• `tra_cuu`: the answer is a short phrase stated verbatim in one sentence.<br>No prompt carries the gold answer or any outcome. |
| Parsing | The last `Nhóm: <id>` label of the visible response. Case is ignored, and backticks and asterisks around the id are ignored. An id outside the list, or no label, is unrecognised. `format_ok` records whether the label is on the last non-empty line. |
| Route and credential | Muse Spark 1.3 Contributor (`muse-spark-1.3-contributor`), registry profile `muse-spark-1-3-contributor`, direct OpenCode Go route (host `opencode.ai`), OpenAI Responses API, not streamed. Each request carries an `x-opencode-session` header derived from its run key. The credential is resolved in the runner process from the local OpenCode auth store, as in MC-86 and MC-89, and is never written to outputs. A non-benchmark probe on 2026-10-28 answered after 244 hidden reasoning tokens; a 300-token cap returned no text. |
| Sampling and limits | Temperature, seed and reasoning effort are not sent, so the provider defaults apply and are not observable. There is no system prompt. `max_output_tokens=4096` covers hidden reasoning and the label. 300 s timeout, no SDK retries. Budget guard 3,000,000 reported tokens (expected about 1 million). |
| Concurrency and halts | At most 4 requests in flight. The run halts when any of these happens: 4 consecutive network failures, a response model id other than the registered one, an authentication error, or the budget guard. Requests already sent finish and are recorded. |
| Retries | No in-run retry. `--resume` re-sends only items without a completed response under an identical frozen condition. Completed responses, including truncated or unrecognised ones, are terminal. |
| Mapping | Cross-draw, with the arms B, Q and S:<br>• Each group's arm is the one with the highest mean token-F1 over the group's items on one draw, and the group's items are scored with that arm's other draw. This runs both ways, and each item's score is the average of the two.<br>• Ties within 1e-12 go to the more thorough arm (B < Q < S).<br>• A group with fewer than 20 items, and every unrecognised output, takes S. S has the best mean token-F1 over all design items (65.9 on ViBidLQA). |
| Keyword comparator | Six regular expressions over the folded question text, frozen in `router_v1.json`, first match wins, otherwise `khac`. They were written from the MC-97 design draws before any router request. They are mapped by the same cross-draw rule. |
| Analysis (fixed before data) | Plan `diagnostic-router-labels-v1`, `python -m code_benchmark.analyze_router_labels --run-dir <output dir>`, run once. Descriptive, because the items are design data. It reports:<br>• the distribution of Muse groups, unrecognised outputs and format compliance;<br>• per Muse group: the items, the mean token-F1 of B, Q and S, and the arm chosen on each draw;<br>• cross-draw routing scores for the Muse grouping, the keyword grouping, always-B, always-Q and always-S, plus the per-item bound;<br>• per-item differences of the Muse grouping against always-S and against the keyword grouping: mean, a percentile bootstrap interval (2,000 resamples, seed 7) and a two-sided sign-flip p-value (20,000 resamples, seed 7);<br>• Muse groups against keyword groups;<br>• the router's mean input, output and reasoning tokens and latency per call.<br>**Reading rule.** The Muse router is called promising when its cross-draw routing score exceeds always-S by at least 1.0 token-F1 point and exceeds the keyword grouping. Otherwise the router line stops at the design stage. |
| Gates | Execution requires all of: the `MC-98` heading in `measurement_card.md`; this detail card; `data/diagnostic_llm_router/registration_labels.json` with the router configuration and manifest hashes above; and a route that resolves to host `opencode.ai`, model `muse-spark-1.3-contributor` and a credential. |
| Provenance and outputs | Everything is under `all_res/diagnostic_llm_router/labels/muse-spark-1-3-contributor/`, with no upload:<br>• `condition.json`: the router configuration, manifest, menu manifest, router module, runner and card hashes; the route; the credential source label, never the key; the limits;<br>• `attempts.jsonl`: per call, usage with reasoning tokens, response model id, latency and the raw visible response;<br>• `labels.jsonl` and `run.json`;<br>• `operator_events.jsonl`, one line per launch. |
| Comparison limits | • The items are design data, and both the groups and the keyword patterns were written after seeing MC-97's draws on them. The cross-draw mapping avoids choosing and scoring on the same draw, but it does not make the check held-out.<br>• Each item gets one router call, so the router's own consistency is not measured.<br>• Muse's provider defaults (temperature, reasoning) are not observable, and its hidden reasoning tokens count as router cost. They are another model's tokens and carry no tariff here.<br>• Token-F1 compares words, not meaning.<br>• An effect near the 1.0-point threshold would need far more than 300 held-out items to be confirmed: MC-96 found 2.4 points on 300 items with p = 0.075. |
