# MC-109 — Qwen3.5-9B (IEC), the self-improvement loop on VMLU test, asked round by round

Registered 2026-11-05 (+07) before benchmark-item requests of this card. The design is `openspec/changes/diagnostic-router-loop`, task 2.9. It does not change MC-90 to MC-108: their registered text, manifests, rules and analyses stand.

| Field | Condition |
| --- | --- |
| Why | **The owner's request.** Fill the VMLU Test column of the /table before-and-after table (`docs/router-before-after/README.md`) for Qwen, starting with Qwen at 6 requests in flight; MiMo later, under its own card.<br>**What is known.** On VMLU valid, MC-105's loop lifted Qwen from 69.9% (its within-run probe) to 82.0% (Holm p below 0.001). VMLU test was not run there, because only vmlu.ai scores it.<br>**What this card asks.** What the same loop gives on the 9,833 test items, as vmlu.ai scores the before and the after. |
| Student / route | **Qwen3.5-9B-65K** (`qwen3-5-9b-65k-prospective`), as MC-105.<br>• **S** uses the IEC endpoint with the campaign transport of `data/diagnostic_prospective_v1/protocol.json`: Responses API, temperature 1.0, system prompt `Answer the user's question.`, 4,096 output tokens, 300 s timeout, no SDK retries.<br>• **B-r1** is the MC-43 probe: chat completions with the user prompt only, temperature 0, seed 42, 4 output tokens, and the top 20 log-probabilities of the first token.<br>The endpoint is reached over the IEC VPN, with the host resolved in-process through the tunnel DNS. The credential comes from `.env` and is never written to outputs. |
| Items | The 9,833 VMLU test items, with the items and prompts of the /table VMLU Test runs. Every item is checked row by row, prompt included, against the frozen v2 VMLU manifest (`data/vi_multimodel_v2/vmlu_v2.json`, self-hash `553fbd77e318eade604911998251e3a32abf743577c28101f8698632eef6b24a`). Gold is withheld; only vmlu.ai scores the split. Qwen answered these items before in MC-70 (OMP without tools) and MC-83 (direct API); no router card used them. |
| Arms | **B:** the frozen v2 VMLU prompt, byte for byte the /table VMLU Test prompt; Qwen's B-r1 is the probe.<br>**S:** the campaign step-by-step template of `data/diagnostic_prospective_v1/prompt_templates_v1.json`, as in MC-90 to MC-105.<br>**Possible attempts:** B-r1, S-r1, S-r2 and S-r3 per item, 39,332 in all.<br>**Files.** Configuration `data/diagnostic_router_loop/vmlu_test_loop_v1.json`, SHA-256 `8d089da71f295d2c10d620ce5fbf1f387ab9d37bdcb67cc848129b0efe27656d`. Manifest self-hash `bbf5ad005884668883e61f4af5320188c8f11f52fdfe90b2eb5386528e9a5866`. Only the hash is frozen: the runner rebuilds the manifest, refuses to run when its hash differs, and writes the copy it ran with into the outputs. |
| The loop | MC-104's and MC-105's rule for Qwen's multiple choice, unchanged:<br>• **Round 1.** Keep B-r1 when its probe confidence is at least 0.80.<br>• **Round 2.** Otherwise keep B-r1 when S-r1 agrees with it.<br>• **Round 3.** Otherwise take the majority of S-r1 to S-r3. A tie goes to the earliest; an empty answer casts no vote; with no answer, S-r1 is final.<br>• **Agreement:** router v2's normalized-answer-v1. Both parsed letters must be non-empty and equal.<br>The final answer is always one of Qwen's own logged answers. |
| Schedule (what differs from MC-105) | MC-105 asked every attempt and replayed the rule offline. Here **each attempt is asked only when the rule needs it**:<br>• the probe for every item;<br>• S-r1 only when the confidence is below 0.80 or missing;<br>• S-r2 and S-r3 only when S-r1 does not agree with B-r1.<br>The attempts are independent requests, so the final answer is the one MC-105's replay (`diagnostic_table_loop.choose`) would choose from the same attempts; the tests check this on 3,000 random cases. The attempts the rule never needs are not sent, so there is no always-S or always-vote policy here.<br>**Passes.** Each pass sends every attempt the rule needs, given the completed attempts so far. An attempt without a completed response (a technical failure, not a fatal one) is sent again in the next pass. A launch stops after 6 passes, after a pass that completes nothing, or at a fatal row; `--resume` continues from the ledger. No pass sends one attempt twice or re-sends a completed one: the runner fails closed if it would, the engine hands each attempt to exactly one lane under a lock, and one output admits one launch at a time (file lock). |
| Scoring | The frozen letter parser. B-r1 is parsed from the probe's reply; S is parsed from the line after the last final-answer label, as in the campaign. A truncated or unparsed reply is an empty answer. |
| Limits | • **In flight:** at most 6 requests, the owner's choice on 2026-11-05 (MC-105: 4), behind one gate shared by the probe and the S requests.<br>• **Breaker:** after 4 consecutive network failures.<br>• **Budget guard:** 20,000,000 reported tokens. Projected from MC-105's VMLU valid rounds and usage: about 1.2 million for the probes and about 9–11 million for S. Expected duration at 6 in flight: about 1 hour of probes and 9–15 hours of S.<br>• **Halts.** On an authentication error, a model-identity drift, the budget or the breaker, as in MC-105.<br>• **Resume.** Completed responses, including truncated ones, are terminal. |
| Gates | Execution requires all of: the `MC-109` heading in `measurement_card.md`; this detail card; `data/diagnostic_router_loop/registration_vmlu_test_loop.json` with the configuration's SHA-256 and the manifest self-hash above; and the campaign endpoint and model in `.env`. |
| Analysis (fixed before data) | Plan `vmlu-test-loop-v1`.<br>• **Outputs.** After each pass the runner writes `loop.jsonl` and `summary.json`. Per item, `loop.jsonl` holds the attempts the rule read, their letters, the probe confidence, the rounds and the final answer. Once every item has a final answer, the runner also writes `submission_before.csv` (B-r1) and `submission_loop.csv` (the loop), both `id,answer` for vmlu.ai.<br>• **Scores.** The owner submits the two files to vmlu.ai, and its reported accuracy for each is entered in the run record.<br>• **Primary.** The loop's accuracy minus the before's, descriptive. With item-level gold withheld there is no paired test.<br>• **Descriptive:**<br>&nbsp;&nbsp;– the rounds the loop used, beside MC-105's VMLU valid rounds (405, 178 and 161 of 744);<br>&nbsp;&nbsp;– how many final answers differ from B-r1;<br>&nbsp;&nbsp;– mean reported tokens per item, the probe included, and latency;<br>&nbsp;&nbsp;– the /table VMLU Test numbers beside the two scores: MC-83 62.94 and MC-70 63.86. |
| Provenance and outputs | `condition.json` holds:<br>• the configuration, manifest, v2 VMLU manifest, campaign protocol, template and source hashes;<br>• the schedule, the loop, the student's settings and the route;<br>• the module, loop-replay, router, wrapper, engine, base engine, shared runner and runner hashes.<br>Also kept: `attempts.jsonl` (raw replies, usage, and the probe's letter log-probabilities), `predictions.jsonl`, `loop.jsonl`, `summary.json`, `run.json`, `source_manifest.json` and `operator_events.jsonl`. They sit under `all_res/diagnostic_router_loop/vmlu_test_loop/<profile>/`. Nothing is uploaded by the runner; the owner submits to vmlu.ai. |
| Comparison limits | • **Before.** The before is the within-run probe at temperature 0 with 4 output tokens. The /table numbers come from other routes and settings (MC-83: Responses API, temperature 1.0, 20,000 tokens; MC-70: OMP without tools).<br>• **One draw.** A second run could differ.<br>• **Prior exposure.** Qwen answered these items before (MC-70, MC-83). A model keeps no memory across requests, but exposure in training to public benchmarks cannot be measured.<br>• **No item-level check.** vmlu.ai returns accuracies only, so neither the gain nor its uncertainty can be tested per item. |
